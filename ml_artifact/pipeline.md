# Детали ML-пайплайна

Этот документ описывает фактическую реализацию в `core/`. Полный запуск выполняет `run.py`, отдельные этапы доступны как `core.ingest`, `core.pipeline`, `core.select_business_news` и `core.rank_business_news`.

## 1. Сбор и нормализация

`core.ingest` читает RSS Markdown-каталог и загружает ленты параллельно. Публикация получает стабильный ID как первые 24 hex-символа SHA-256 от `source + "\\n" + url`. После загрузки записи сортируются по дате и дедуплицируются по `post_id`. Изображения проверяются Pillow и получают SHA-256 и perceptual hash.

Интервал полуоткрытый: `start <= date < end`; даты нормализуются к UTC. Ошибка отдельного источника попадает в `ingest_report.json` и не останавливает остальные загрузки.

## 2. Очистка и ruBERT

`load_slice` читает все `*.jsonl` из `raw_dir`, пропускает строки с некорректным JSON или датой и сортирует их хронологически. `clean_text` удаляет URL, `@mentions` и лишние пробелы.

`RubertOnnxClassifier` использует `models/rubert_int4/model.onnx`, токенизатор и пороги `metadata.json`. Максимальная длина — 256 токенов; модель имеет 31 выход, включая `Реклама/мусор`.

| Условие | Статус |
| --- | --- |
| очищенный текст короче 40 символов | `short_or_empty`, ruBERT не вызывается |
| ни одна категория не прошла свой порог | `no_labels`, публикация удаляется |
| есть `Реклама/мусор` | `ad_or_spam`, публикация удаляется |
| есть тематические метки без spam | `kept`, публикация идёт дальше |

Предсказания сохраняются построчно в `predictions.jsonl`. При `--predictions` для каждой записи входного среза должна существовать соответствующая строка с тем же `post_id`.

## 3. BGE-M3 и кеш

Для `kept`-публикаций берутся первые 1200 символов очищенного текста. BGE-M3 INT8 использует лимит 512 токенов, CLS pooling и L2-нормализацию; размер вектора — 1024.

Кеш `embeddings_<sha256>.npz` зависит от модели, pooling, лимита символов, `post_id` и текста. Он проверяется на размерность, конечность значений и единичную норму.

## 4. Кластеризация событий

Публикации должны быть хронологическими. Для каждой публикации `cluster_posts`:

1. оставляет кластеры, активные последние `window_hours`;
2. исключает кластер с тем же `channel`;
3. считает cosine к центроиду суммы векторов;
4. оставляет максимум `retrieval_top_k` кандидатов с cosine не ниже порога;
5. передаёт максимум `rerank_top_k` кандидатов в локальный BGE reranker;
6. присоединяет публикацию только если лучший raw logit не ниже `reranker_threshold`;
7. иначе создаёт новый кластер.

Рабочие значения: окно 24 часа, cosine `0.78`, top-8, raw logit `0.0`. Logit не является вероятностью. Кластеры не сливаются задним числом, поэтому результат зависит от порядка и параметров запуска.

Кластер содержит `event_id`, `members`, `sources`, агрегированные `labels` и до четырёх уникальных `images`. Дубликаты изображений определяются по `image_id`/SHA-256 и perceptual hash. `clusters_browser.html` автономен и не требует web-сервера.

## 5. Профиль компании и кандидаты

`business_source_selection` фильтрует публикации до расчёта агрегированных меток и числа источников. Подборка строится из RSS-каталога по профилю: до 40 RSS-источников на профиль.

`select_business_news` строит профиль из `reference_uids.json` и порогов ruBERT. Активных категорий (`прямое` + `косвенное`) не более восьми; остальные имеют уровень `не важно`. Переопределения передаются через `--profiles`:

```json
{
  "U_71020": {
    "Логистика и перевозки": "прямое",
    "Налоги и налоговое администрирование": "косвенное"
  }
}
```

Для меток кластера score ниже порога отбрасывается, `Реклама/мусор` даёт `excluded`, а максимальный уровень совпавшей категории становится `impact`. Событие без влияния обычно получает `ignored`; более пяти независимых групп источников сохраняют событие как кандидат для дальнейшего решения.

Независимая группа определяется после нормализации источника. `source_group` и `original_source` могут объединять перепечатки; известные связи задаются в `SOURCE_GROUPS`. Без этих полей уникальный канал считается отдельной группой, поэтому независимость — приближение.

## 6. Маршрутизация LLM

Текущие модели и роли:

| Роль | Модель | Условие |
| --- | --- | --- |
| Screening | `qwen/qwen3.6-35b-a3b` | событие с косвенным влиянием |
| Финальный анализ | `moonshotai/kimi-k2.6` | прямое влияние или положительный screening |

Запросы используют `temperature=0`, `reasoning_effort=none`, `max_tokens=2048`. Основной и резервный HTTPS gateway задаются `--base-url` и `--fallback-url`. Ключ берётся из `ALFA_LLM_API_KEY` или `--env`.

До LLM удаляются публикации вне подборки компании. В обработку попадают только `прямое` и `косвенное` влияние; большое число источников не заменяет категориальный фильтр профиля.

### Qwen screening

Qwen получает компанию, профиль, источники события, финансовую выжимку, аналитику банка и темы. Возвращает четыре boolean-поля:

```json
{"related":true,"direct":false,"fact":true,"within_month":true}
```

При `related=false` остальные флаги должны быть `false`. Нулевая оценка даёт `weak`; положительная переводит событие в финальный Kimi-анализ.

### Kimi final

Kimi получает фактический контекст, но не получает отдельную оценку Qwen. Возвращает флаги связи, тезисы `why`, текст карточки, ключевые факты, позицию банка и, при наличии `--topics`, `topic_id`.

`topics.json`:

```json
[{"topic_id":"rate-cut","title":"Ключевая ставка","summary":"Изменения ставки и последствия"}]
```

`context.json`:

```json
{"financial_summary":"Краткая выжимка отчётности","bank_analytics":["Фрагмент аналитики"]}
```

Если найден переданный `topic_id`, результат получает `tracked` и `badge: Обновление`; в основную ленту он не попадает. Иначе важность считается кодом:

```text
I = 40 * related + 25 * direct + 20 * fact + 15 * within_month
```

`I >= 50` → `feed`, `I < 50` → `weak`. Для ленты добавляется затухание свежести:

```text
rank_score = I * 2 ** (-age_hours / half_life_hours)
```

`half_life_hours` по умолчанию 72; дата расчёта задаётся `--as-of` или берётся из последней публикации корпуса.

Событие с более чем пятью независимыми группами помечается `qwen_multi_source`. Если старый результат ещё не был финальным Kimi, пересечение порога может вызвать повторный анализ; уже финальный Kimi повторно не вызывается.

## 7. Кеш и повторный запуск

`api_cache/` хранит ответы LLM и историю попыток, `state/` — результаты событий текущей конфигурации, `runs/` и `requests.jsonl` — метрики и журнал. Ключ состояния зависит от версии маршрутизации, профиля, аккаунта, тем, контекста, порогов, корпуса, параметров кластеризации и моделей.

После `Ctrl+C` последний checkpoint остаётся на диске, повтор той же команды продолжает обработку. `requests.jsonl` содержит модель, этап, статус, latency, usage и стоимость, но не API-ключ и prompt-тексты. Если gateway не вернул `usage.cost`, стоимость неизвестна; `--pricing` задаёт подтверждённые тарифы для отдельной оценки `estimate`.

## 8. Метрики и ограничения

`*_metrics.json` и поле `metrics` итогового JSON содержат размер корпуса, число публикаций после ruBERT, число кластеров, статусы событий, API-вызовы, кеш-попадания, повторы, ошибки, токены, стоимость, latency, независимые источники и маршруты screening/final.

Единица обработки — событие-кластер. Precision, recall, NDCG, точность классификации и качество LLM не вычисляются без эталонной разметки. Порог cosine `0.78` и raw logit `0.0` — стартовые значения, требующие калибровки на размеченных парах событий.
