# Интеграция ML-пайплайна с лентой: дизайн

## Цель

Подключить реальный ML-пайплайн к рабочей новостной ленте, сохранив существующие Telegram/RSS-сборщики и API-контракт `NewsEvent`, а текущую директорию `ml/` целиком переименовать в `ml_artifact/`.

## Решения

- Обработка выполняется отдельным фоновым worker-процессом.
- Worker читает новые `Post` из общей PostgreSQL-базы. Он не собирает Telegram или RSS самостоятельно.
- `ml/` переименовывается в `ml_artifact/` без потери содержимого: модели, ноутбуки, старый CLI, результаты и документация остаются там.
- Runtime-код worker размещается в новой `ml_pipeline/`.
- Медиа входных постов сохраняются отдельно от БД в общем Docker volume; БД содержит метаданные, контрольные суммы и относительные пути.
- `NewsEvent` является записью кластера, а не записью одного входного поста. В одной записи хранятся публикации разных источников в `source_posts`, агрегированные категории, ссылки и до четырёх уникальных изображений кластера. Персональный отчёт, исходные булевы оценки и `impact` хранятся в `EventAnalysis` для пары «профиль + событие»; итоговую важность `I` рассчитывает фронтенд.
- Порог разделения основной и слабой выдачи равен `30` и задаётся конфигурацией. Фронтенд показывает основную группу при `I > 30`, а слабую группу при `I < 30`.
- Кластер без совпадения категорий профиля не вызывает персональный LLM-анализ и не попадает в основную ленту.
- Сбои обрабатываются автоматически: worker повторяет попытки с лимитом, затем помечает `Post` как `failed` и сохраняет причину.

## Поток данных

1. `tg-ingest` получает текст и изображения сообщения Telegram; RSS-поллер извлекает media enclosures, thumbnails и Open Graph image. Оба источника передают текст, метаданные и изображения в ingest.
2. `POST /api/ingest/posts` принимает JSON новости вместе с необязательными image files. API сохраняет файлы в общий media volume и нормализованные метаданные изображения. Он сохраняет `Post` со статусами `received`/`stage=received`; HTTP-ответ не ждёт ML-обработки. Переданный `profile_id` сохраняется в исходном payload для совместимости, но не ограничивает worker одним профилем.
3. Worker атомарно захватывает batch необработанных `Post` через PostgreSQL row lock и lease, упорядочивает их по времени публикации и сначала обрабатывает классификацию батчем.
4. Worker очищает текст и запускает ruBERT. Текст короче 40 символов, пост без меток или пост с меткой `Реклама/мусор` исключаются из событий. Для оставшихся постов BGE-M3 строит 1024-мерный нормированный embedding по первым 1200 символам. Публикации кластеризуются хронологически: под транзакционной advisory lock выбираются кластеры, активные последние 24 часа, исключается кластер, уже содержащий тот же канал, cosine-кандидаты с порогом `0.78` проходят top-8 BGE reranker. При лучшем raw logit `>= 0.0` пост присоединяется к выбранному кластеру; иначе создаётся новый кластер.
5. Для нового кластера создаётся ровно один `NewsEvent`; для присоединённого поста обновляется эта же запись: добавляются публикация, source, URL и медиа, а агрегированные категории получают максимальные значения по участникам. Дубликаты медиа удаляются по image id/SHA-256 и perceptual hash, максимум четыре изображения.
6. После фиксации кластера worker проходит все активные профили. Публикации кластера фильтруются по подпискам на источники конкретного профиля; категории и число независимых источников пересчитываются по оставшимся участникам. Если профильные категории не совпали, LLM не вызывается. Совпавшие категории определяют уровень влияния (`direct` или `indirect`) и маршрут LLM. Персональный результат сохраняется в `EventAnalysis`.
7. `/api/feed` возвращает клиенту персональные результаты и компоненты оценки `related`, `direct`, `fact`, `within_month`, а также профильное число независимых источников. Фронтенд рассчитывает `I = 40*related + 25*direct + 20*fact + 15*within_month`, выводит все новости с `I > 30` по убыванию `I`, затем добавляет до 10 новостей с `I < 30`, отсортированных по убыванию числа независимых источников. Равные значения разрешаются по дате публикации от новых к старым.

## Компоненты

### `ml_artifact/`

Полный перенос текущего `ml/`. Пути в README, CLI и конфигурации обновляются на новое имя. Секреты, Telegram-сессии, локальные виртуальные окружения, кэши и генерируемые outputs не становятся runtime-зависимостями worker.

### `ml_pipeline/worker.py`

Асинхронный цикл polling: чтение настроек, захват batch, обработка, commit, backoff и logging. Worker должен поддерживать graceful shutdown.

### `ml_pipeline/adapter.py`

Граница между SQLAlchemy и ML-функциями. Преобразует `Post` вместе с медиа в нормализованный ML-вход и переводит результат в поля `Post`, кластерный `NewsEvent`, `EventAnalysis` и `TrackedItem`. ML-модули не импортируют ORM.

### Backend ingest

`POST /api/ingest/posts` перестаёт вызывать полный синхронный `ingest_from_profile`. JSON payload сопровождается image files; сервер сохраняет файлы и `Post` одной операцией, затем возвращает статус приёма. Профиль из payload сохраняется как метаданные обратной совместимости; worker строит оценки для всех активных профилей, чтобы один кластер мог иметь разные результаты.

### Сбор медиа

`tg-ingest` скачивает изображения сообщения Telegram и отправляет их вместе с payload. RSS-парсер извлекает media enclosures и thumbnails, а при их отсутствии пробует Open Graph image страницы; изображения сохраняются тем же media storage helper. Ошибка отдельного изображения не отбрасывает текст новости.

### Backend feed

Запрос ленты соединяет `NewsEvent` с `EventAnalysis` текущего профиля и возвращает достаточно кандидатов, включая слабые события, с исходными компонентами персональной оценки и числом независимых источников после фильтрации источников профиля. Фронтенд рассчитывает `I = 40*related + 25*direct + 20*fact + 15*within_month`; новости с `I > 30` показывает по убыванию `I`, а затем добавляет до 10 новостей с `I < 30` по убыванию количества независимых источников. При равенстве используется дата публикации от новых к старым. Устаревшие события без ML-оценки могут использовать существующий fallback на `match_event`, который также должен предоставлять необходимые компоненты либо оставаться вне нового персонального списка. Клиент не применяет затухание `rank_score` при сортировке. Общие факты и все источники берутся из `NewsEvent`. API возвращает media URL участников через существующую схему `SourcePostOut.image_url`; фронтенд использует их при отображении карточки события.

### Медиа и кластерная запись

`Post.media` хранит медиа входной публикации в нормализованном JSON-формате (`image_id`, относительный путь локального файла, origin URL, source, SHA-256, perceptual hash и размеры при наличии). `NewsEvent.source_posts` содержит участников кластера с `post_id`, source, date, text, URL, media и метками ruBERT; `NewsEvent.media` — агрегированный список уникальных медиа для карточки события, не более четырёх изображений. Дедупликация использует image id/SHA-256 и perceptual hash. Вектор кластера строится из embeddings `Post`, уже связанных с этим `NewsEvent`; `chain_key` хранит стабильный ключ кластера. Изображения не сохраняются и не показываются, если имя источника после приведения к нижнему регистру и нормализации пробелов совпадает с одним из запрещённых источников: «агентство нефтегазовой информации», «взгляд», «интерфакс», «кошелек onliner», «независимая газета», «право ру», «прайм», «профиль», «российская газета», «утро ру», «учительская газета», «хабр лучшее за неделю», «advertology.ru», «alta.ru», «bfm.ru», «drom.ru», «new retail», «open net», «regnum», «rt на русском». Публикации этих источников остаются в кластере и участвуют в подсчёте независимых источников; ограничение относится только к медиа.

## Состояния и ошибки

`Post.status` описывает общую обработку источника и использует состояния `received`, `processing`, `clustered`, `retry` и `failed`. `Post.news_event_id` и `Post.cluster_key` фиксируют кластер источника. Персональные решения `feed`, `weak`, `tracked` и `ignored` хранятся в `EventAnalysis.status`, поскольку один кластер может быть релевантен профилям по-разному. Миграция добавляет в `Post` поля `media`, `attempt_count`, `lease_until`, `last_error` и время обновления статуса; в `NewsEvent` — агрегированное поле `media`; в `EventAnalysis` сохраняются структурированные булевы компоненты Kimi/Qwen, необходимые API для клиентского расчёта `I`, а также персональные `status` и `impact`. Backend не отбрасывает слабые события до выдачи клиенту.

Захват выполняется транзакционно с `FOR UPDATE SKIP LOCKED`; истёкший lease позволяет повторно взять зависшую запись. Кластерное сопоставление и изменение выполняются под транзакционной advisory lock, чтобы два worker не создали разные кластеры для параллельных похожих публикаций. Вложение источника идемпотентно по `Post.id`. Если `Post.news_event_id` уже задан, retry возобновляет обработку профилей и не создаёт дубликат кластера. Уникальность `EventAnalysis(profile_id, event_id)` обеспечивает upsert персональной оценки. Неповторяемые ошибки данных и исчерпание лимита попыток переводят `Post` в `failed` и сохраняют причину.

## Конфигурация и запуск

В корневой `docker-compose.yml` добавляется сервис `ml-worker`, подключённый к той же PostgreSQL, каталогу моделей и общему media volume. Конфигурация включает `ML_WORKER_ENABLED`, интервал polling, размер batch, lease timeout, максимальное число попыток, порог `ML_FEED_THRESHOLD=30`, пути к `ml_artifact` и модели LLM.

Compose, `.env.example`, `README.md` и `docs/DEPLOY.md` описывают запуск полного стека. Worker не требует отдельного Telegram-сеанса и не дублирует RSS-поллер.

## Проверка

- Тесты ingest проверяют загрузку Telegram-фото, RSS enclosure/thumbnail/Open Graph image, сохранение файла и метаданных, а также продолжение обработки текстовой новости при ошибке отдельного изображения.
- Unit-тесты адаптера проверяют отбрасывание short/no-label/spam, маппинг входного медиа, присоединение нескольких источников к одному событию, агрегацию категорий максимумом и дедупликацию медиа.
- Frontend-тесты проверяют расчёт `I` из булевых компонентов, сортировку основной ленты по убыванию `I`, добавление не более 10 слабых новостей по числу независимых источников и разрешение равенств по дате публикации.
- Frontend smoke test проверяет отображение разрешённых media URL кластерных источников и отсутствие изображений запрещённых источников, не скрывая сами публикации и не нарушая fallback для старых событий.
- Интеграционные backend-тесты проверяют асинхронный ingest, конкурентный захват, lease, retry/failed и персональную выдачу `/feed`.
- ML-тесты сохраняются и переносятся вместе с `ml_artifact/`; добавляется тест реального worker на фикстурном batch без сетевых вызовов.
- Проверяется, что профиль с разными категориями получает разные score и порядок одних и тех же `NewsEvent`.
- Запускаются `pytest`, `ruff check`, сборка frontend и существующие Playwright smoke-тесты.

## Ограничения

- Первый этап не добавляет отдельную таблицу кластеров: существующие `Post`, кластерный `NewsEvent`, `EventAnalysis` и `TrackedItem` остаются контрактом.
- Отдельный event на профиль не создаётся.
- Перекластеризация старых исторических данных не выполняется автоматически; для неё нужен явный batch-запуск.
- Порог `30` и другие параметры должны быть конфигурационными, поскольку продуктовая спецификация может измениться.

## Точная маршрутизация LLM

- Прямое влияние (`direct`) сразу вызывает финальный анализ Kimi.
- Косвенное влияние (`indirect`) сначала вызывает Qwen screening с полями `related`, `direct`, `fact`, `within_month`.
- Если Qwen подтверждает связь, событие передаётся в финальный Kimi-анализ; если связь не подтверждена, персональный score равен `0` и событие остаётся слабым.
- Финальный Kimi получает кластер, все его источники и профиль, но не получает отдельную оценку Qwen, чтобы не подстраиваться под неё.
- Kimi возвращает `related`, `direct`, `fact`, `within_month`, `why`, `card_text`, `key_facts` и `bank_position`. Фронтенд считает персональную важность `I = 40*related + 25*direct + 20*fact + 15*within_month`.
- Фронтенд считает `I = 40*related + 25*direct + 20*fact + 15*within_month`. `I > 30` попадает в основную ленту по убыванию `I`; из `I < 30` добавляются до 10 событий по убыванию числа независимых источников. При равенстве используется дата публикации от новых к старым. Сортировка по затухающему `rank_score` для этой ленты не применяется.
- Независимые группы источников нормализуются с учётом `source_group`/`original_source` и известных связей; несколько постов одного канала считаются одним источником.
- Для персонального анализа и подсчёта независимых источников учитываются только публикации из источников, выбранных для профиля.
