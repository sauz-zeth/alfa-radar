# Цепочки обновлений новостей

Oct 17, 2026 · @alex

## Кратко

Пайплайн находит новые события, которые продолжают истории из вкладки «Интересное», и сразу присылает подписчикам отчёт о том, что изменилось. Отслеживаются только цепочки, которые кто-то отметил как интересные (порядка сотни), поэтому поиск — это одно матричное умножение, а LLM вызывается только для близких пар.

Пайплайн запускается после шага 2 основного пайплайна (кластеризация в события) для каждого нового события, параллельно шагам 3–6. Шаги 1–3 считаются один раз на событие, шаг 4 — на пару «цепочка + компания» и кешируется, шаг 5 — на пользователя.

Большинство событий отсеивается на пороге без вызова LLM. До отчёта и уведомления доходят только события, которые LLM признала продолжением с новым фактом.

## Данные

Нужны три таблицы в Postgres. Векторы цепочек хранятся там же: при сотне цепочек отдельная векторная база не нужна.

**chains** — отслеживаемые цепочки.

| Поле | Смысл |
| --- | --- |
| chain\_id | id цепочки |
| vector | эмбеддинг последнего события цепочки (multilingual-e5-base, нормированный) |
| last\_event\_id | последнее событие цепочки |
| last\_update | t0 последнего события |
| summary | заголовки и даты последних 3 событий + what\_changed, вход для LLM на шаге 2 |
| status | active / closed |

**chain\_events** — история цепочки, из неё строится таймлайн.

| Поле | Смысл |
| --- | --- |
| chain\_id | id цепочки |
| event\_id | событие из основного пайплайна |
| t0 | время первой новости события |
| what\_changed | фраза от LLM; пусто у первого события |

**chain\_subscribers** — кто отслеживает цепочку.

| Поле | Смысл |
| --- | --- |
| chain\_id | id цепочки |
| user\_id, company\_id | подписчик и его компания |
| last\_report\_id | последний отчёт по цепочке для этой компании, вход для шага 4 |
| subscribed\_at | время свайпа вправо |

Старые векторы не удаляются из истории: в `chains.vector` заменяется только активный вектор, а события остаются в `chain_events`.

## Офлайн-подготовка

До запуска подбирается один порог θ\_ch — минимальное сходство, при котором пара идёт в LLM.

1. Набор пар «новое событие + цепочка», около 150 штук, из архива новостей за 1–2 месяца.
2. Положительные пары — следующий шаг той же истории: слух → решение, решение → последствия.
3. Отрицательные пары берутся трудные: та же тема с другими участниками («ставку повысил ЦБ» и «ставку повысил Сбер»), перепечатка без нового факта, колонка с мнением.
4. LLM размечает пары, 50 проверяются вручную.
5. θ\_ch — максимальный порог, при котором recall продолжений не ниже 0.95. Точность обеспечивает LLM на шаге 2, поэтому порог настраивается на полноту. Стартовое значение — 0.75.

На этих же парах меряется качество шага 2: precision и recall решения LLM.

## Шаг 1. Поиск кандидатов

Новое событие сравнивается со всеми активными цепочками по косинусу, в LLM идут до трёх ближайших выше порога.

Шаг запускается, когда на шаге 2 основного пайплайна создаётся новое событие. Если к существующему событию просто добавился источник, это не продолжение, а тот же факт: шаг 1 не запускается.

Вход: e — эмбеддинг события (центроид его новостей, нормированный), t0 — время первой новости. V — матрица векторов активных цепочек, по строке на цепочку.

```latex
s = V \cdot e
```

```latex
\text{cand} = \operatorname{top3}\{\, k : s_k \ge \theta_{ch},\ t_0 > \text{last\_update}_k \,\}
```

- Векторы нормированы, поэтому скалярное произведение равно косинусу. При 100 цепочках и векторах размерности 768 это доли миллисекунды в numpy.
- Условие t0 > last\_update отсекает старые новости, пришедшие с опозданием.
- Кандидатов нет — событие идёт дальше только по основному пайплайну, LLM не вызывается. Так будет с большинством событий.
- Для e5 эмбеддинги считаются с одинаковым префиксом `passage:` и у событий, и у цепочек: сравниваются тексты одного типа.

## Шаг 2. Проверка в LLM

LLM получает новое событие и до трёх кандидатов и решает, продолжает ли событие одну из цепочек и есть ли в нём новый факт.

Вход: заголовки и тексты до 3 источников события, его t0; для каждого кандидата — chain\_id и summary из таблицы chains. Профиль компании не передаётся: вопрос «продолжение ли это» общий для всех пользователей, поэтому шаг выполняется один раз на событие.

Ответ проверяется Pydantic-схемой, при ошибке запрос повторяется.

| Поле | Тип | Смысл |
| --- | --- | --- |
| chain\_id | строка или null | цепочка, которую продолжает событие; null — ни одна |
| has\_new\_fact | bool | есть новый факт, а не перепечатка, мнение или пересказ |
| what\_changed | строка | одна фраза «что изменилось» для карточки и уведомления |

Событие добавляется в цепочку, только если chain\_id не null, входит в список кандидатов и has\_new\_fact = true.

- В промпте прямо сказано: при сомнении отвечай null. Ложная склейка дороже пропуска: пользователь получит уведомление о чужой истории.
- Модель — быстрая и дешёвая, через тот же шлюз LiteLLM. Задача узкая и с коротким ответом.

## Шаг 3. Обновление цепочки

Событие становится последним звеном цепочки, и вектор цепочки заменяется его вектором.

1. В chain\_events добавляется строка: chain\_id, event\_id, t0, what\_changed.
2. В chains: vector ← e, last\_event\_id ← событие, last\_update ← t0, summary пересобирается из последних 3 событий.
3. Для подписчиков цепочки событие помечается как обновление и не попадает в их ленту, чтобы не показывать его дважды. Для остальных пользователей событие идёт по основному пайплайну как обычно.

Вектор заменяется, а не усредняется: следующее обновление обычно похоже на последнее состояние истории, а не на её начало. Если к последнему событию цепочки потом приходят новые источники, его центроид уточняется, и vector цепочки обновляется вместе с ним.

## Шаг 4. Отчёт об изменениях

Для каждой компании-подписчика LLM пишет отчёт о том, что изменилось с прошлого отчёта и меняет ли это выводы.

Вход: профиль компании, прошлый отчёт по цепочке для этой компании (last\_report\_id), новое событие и what\_changed. Отчёт пишется заново не целиком, а как разница с прошлым: так дешевле, и руководителю не нужно перечитывать всё.

| Поле | Тип | Смысл |
| --- | --- | --- |
| change | строка | что изменилось для компании, 2–3 предложения |
| conclusions\_changed | bool | меняет ли обновление выводы прошлого отчёта |
| materiality | 1–5 | влияние на выручку или затраты, как в шаге 5 основного пайплайна |
| certainty | 1–5 | насколько событие подтверждено |
| impact | risk / opportunity | тип влияния |
| actions | список строк | что проверить или кому передать, если выводы изменились |

Важность I считается той же формулой, что и в основном пайплайне:

```latex
I = 20 \cdot M \cdot \left(0.6 + 0.4 \cdot \frac{C}{5}\right)
```

Кеш по ключу «цепочка + событие + компания»: два руководителя одной компании получают один отчёт. Отчёт генерируется сразу, а не после свайпа: обновление отслеживаемой истории идёт прямо в «Интересное».

## Шаг 5. Уведомление

Обновление всегда появляется в «Интересном», а пуш получают только значимые обновления и не больше трёх в день.

1. Карточка в «Интересном» поднимается наверх с бейджем «Обновление» и строкой what\_changed. В подробном разборе — отчёт шага 4 и таймлайн цепочки из chain\_events.
2. Пуш отправляется, если conclusions\_changed = true или I ≥ 50.
3. Не больше 3 пушей в день на пользователя. Сверх лимита обновление остаётся в «Интересном» без пуша.

Текст пуша: «Обновление: {заголовок цепочки}. {what\_changed}».

## Жизненный цикл цепочки

Цепочка появляется со свайпом вправо и закрывается, когда у неё нет обновлений или подписчиков.

| Событие | Что происходит |
| --- | --- |
| свайп вправо, событие не в цепочке | создаётся цепочка: vector = эмбеддинг события, пользователь — первый подписчик |
| свайп вправо, событие уже в цепочке | пользователь добавляется в подписчики, отчёт шага 4 строится от текущего состояния |
| кнопка «Не отслеживать» | пользователь удаляется из подписчиков |
| у цепочки не осталось подписчиков | status = closed |
| нет обновлений 14 дней | status = closed |

Закрытая цепочка не участвует в шаге 1, но её история остаётся в chain\_events. Без закрытия набор цепочек растёт бесконечно, и старые темы начинают ловить случайные совпадения.

## Объёмы и стоимость

Основной расход — LLM на шагах 2 и 4, и он зависит от числа кандидатов выше θ\_ch. Оценки ниже приблизительные, точные цифры даёт журнал вызовов LLM.

| Шаг | Объём в день | Расход |
| --- | --- | --- |
| 1. Поиск кандидатов | 5–7 тыс. событий × \~100 цепочек | \~700 тыс. косинусов, доли секунды в numpy |
| 2. Проверка в LLM | события выше θ\_ch, ожидается порядка сотен | короткие вызовы быстрой модели |
| 4. Отчёт | обновления × компании-подписчики | вызовы полноценной модели, кешируются по компании |
| 5. Уведомления | не больше 3 на пользователя | — |

Векторная база понадобится, когда активных цепочек станут тысячи: тогда матрица V переезжает в pgvector без изменения логики.

## Метрики качества

Каждый шаг проверяется на размеченных парах, а польза уведомлений — по поведению пользователей.

| Компонент | Метрика | Данные |
| --- | --- | --- |
| Поиск кандидатов | recall продолжений при θ\_ch, доля событий в LLM | 150 пар из офлайн-подготовки |
| Проверка в LLM | precision и recall склеек | те же пары, 50 проверены вручную |
| Уведомления | доля открытых пушей; доля «Не отслеживать» после пуша | логи пользователей |
| Продукт | доля обновлений, приведших к действию (вклад в North Star) | логи пользователей |
